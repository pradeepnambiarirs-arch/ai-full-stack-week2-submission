### Runtime, interface and verification

- **Runtime:** Python 3.11+ on Linux, using argparse, sqlite3, hashlib, concurrent.futures, urllib.request and unittest; this keeps deployment small and supports independent CLI operator processes.
- **Interface:** `python3 -m access_intake` with `intake`, `resume`, `queue`, `show`, `history`, `retry`, `refresh`, `export`, `accuracy` and `verify` subcommands; a CLI meets the brief and supports remote operators connecting to one shared host.
- **Storage:** one SQLite database on local disk on a single host, with foreign keys, WAL, `synchronous=FULL` and a configurable busy timeout (initially 5 seconds); multiple operator processes use the same database. WAL permits concurrent readers and a writer but requires same-host access, so sharing the database file over NFS or between hosts is outside the supported boundary. Regional operators use SSH to the shared host. A multi-host database deployment is not specified by the brief. [SQLite WAL documentation](https://www.sqlite.org/wal.html)
- **Schema:** explicitly use `jsonschema.Draft202012Validator` and `check_schema` on the unchanged supplied schema, with separate semantic date/evidence checks; choose and pin the tested dependency version and transitive hashes in `requirements.lock` during implementation. An explicit class avoids the package's changing default dialect when `$schema` is absent. [jsonschema validation documentation](https://python-jsonschema.readthedocs.io/en/stable/validate/)
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`; use temporary SQLite databases, deterministic fake clocks, process barriers and injected transport/credential suppliers. Apply a suite-wide network-denial guard. Every executable test uses saved responses or saved failure descriptors under tests/mock_responses/; convert the two standalone supplied-file/schema starter checks into fixture-backed checks in S01 rather than leaving exceptions. No test reads API_KEY, calls a real model or invokes the production environment credential loader. The shell removes API_KEY before interpreter launch; do not inspect or copy the process environment inside tests.
- **Provider sequence:** first a deterministic fixture provider, then an OpenAI Responses adapter over injected HTTP transport. Mock fixtures reproduce transport and validation behavior; they do not demonstrate live-model factual accuracy.

### Provider contract and configurable real integration

A provider receives the decoded source message and immutable processing configuration, returning either a complete response envelope or a typed failure. The mock is keyed by an explicit test manifest (source digest/configuration/call sequence), never by production request IDs to infer business facts; an unknown mock input fails visibly. `tests/mock_responses/canned-reply.json` is a starter connectivity example, not a schema-conforming extraction fixture.

The real adapter uses `POST https://api.openai.com/v1/responses`, `Authorization: Bearer <API_KEY>`, separate trusted instructions and untrusted user message, and `text.format` with `type=json_schema`, `name=access_snapshot`, `strict=true` and the supplied schema. It sends no tools and gives the model no approval capability. Its instructions require explicit facts, exact quotes, null/issue handling, corrections and requested new permission. [Structured Outputs documentation](https://developers.openai.com/api/docs/guides/structured-outputs)

Propose `gpt-5.4-mini-2026-03-17` as the documented supported model, with `reasoning.effort=none`, `max_output_tokens=4096`, `store=false`, non-streaming requests and a 60-second request timeout; model and request configuration are overridable. This model's documentation lists Responses and structured-output support; actual account access remains unverified. Do not silently fall back to another model. [Model documentation](https://developers.openai.com/api/docs/models/gpt-5.4-mini.md)

Validate HTTP success, top-level response completion, refusal content, completed output-message status, exactly one extraction text payload, JSON shape, supplied schema and semantic evidence before routing. A parseable body with incomplete status is still a failure. Record provider/model from the response where supplied, as well as requested configuration, without pretending mocked HTTP responses came from a live provider. Preserve request IDs and sanitized error classes, never authorization headers or raw provider exceptions that might contain secrets. [Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create)

Proposed nonsecret config is JSON loaded with `--config`; selectors include provider (`mock` or `openai`), model, endpoint, generation settings, prompt/schema paths, timeout, rate limit, worker limit and policy version. API_KEY is read only by the real adapter's credential loader. Tests bypass that loader by injecting a credential supplier returning a fabricated sentinel directly; they do not read API_KEY even from a test mapping. Inspect the production environment-to-credential wiring statically for R-76, and verify bearer-header construction through injected transport. This deliberately adapts the spec's suggested sentinel-environment check to the user's stricter no-API_KEY-read condition; live environment integration remains unexecuted. Record only effective nonsecret values in provenance. Operational knobs such as worker count do not invalidate successful facts; output-affecting provider/model/request settings do.

### Data model, concurrency and transaction boundaries

Use separate tables for documents, immutable source revisions (original bytes, original filename, SHA-256 and ingestion metadata), immutable configuration/policy snapshots, processing jobs, attempts, append-only activity events and one current-result pointer per document. Each result contains extraction plus status/owner/next_action/error together, so the queue is a database view of the same record, not a separately updated mutable table. Keep attempt/result history separate from current exported outputs; retain it without automatic deletion for this exercise. Foreign keys associate every attempt with its exact source, model configuration, policy and prompt/schema versions.

Import a batch as per-document short transactions. The source hash is `sha256(original_bytes)`, before JSON parsing or normalization; document_id remains the basename including `.json`. Repeated request_id values across filenames do not merge documents. Reject duplicate basenames within one batch with a visible input error; operators must namespace separate feeds by database because the brief supplies no cross-directory identity rule. Unreadable, invalid UTF-8/JSON or missing/non-string-message inputs get recorded input errors where filename identity is known; other files continue. Do not invent an overlength or non-English acceptance guarantee.

Use explicit `BEGIN IMMEDIATE` for registration, job claims and publication, with commit/rollback and bounded busy handling. Give each thread its own connection. Read-only queue/show/history commands use short read snapshots. A busy writer must return an actionable operational failure after its timeout rather than bypassing coordination; a model call never runs while a write transaction is held. SQLite allows one simultaneous writer, so these small critical sections serialize changes while model calls remain concurrent. [SQLite transaction documentation](https://www.sqlite.org/lang_transaction.html)

A transaction claims at most one eligible job and assigns a worker identity, a lease expiry and a monotonically increasing claim token; a uniqueness constraint prevents two active claims for the same desired document generation. The global in-flight limit (initially 4 across all processes) and request-start pacing (initially 30/minute, configurable) live in the database, not per-process counters. A second operator joins existing pending jobs instead of creating duplicates. Different-source registration creates a higher desired generation and supersedes older pending jobs. Publication checks both the claim token and desired generation before atomically inserting the outcome and advancing the current pointer. A late old worker may add a superseded historical outcome but cannot overwrite a newer current record, even if its response completes last.

Choose ingestion transaction order as revision precedence; exported_at and request_date are not revision sequence numbers. An unchanged import against the desired revision is a no-op, while an explicit reimport of older bytes after a correction is treated as a new operator intent and must be visible in history. This is a proposed operational ordering convention, not a policy-defined business rule.

### Resumption, visibility, retries and history

Jobs have queued/running/finished/superseded operational states, separate from business queue statuses. Each terminal attempt (success or failure) commits immediately; later documents do not wait for a whole batch or input-order collection. A separate `queue --watch` process opens a fresh read snapshot per poll. Show the current terminal outcome with source hash/configuration, plus pending-refresh metadata; label a previous successful result as the previous version while a newer generation is pending. A new document without a terminal outcome appears as pending work, never as a fabricated successful extraction. Submission exports require no pending desired generations.

A worker renews its lease every 10 seconds (initial lease 120 seconds), using the fake clock in tests. On SIGINT stop taking new claims and finish or persist interrupted work where possible. A crash may prevent finalization: `resume` atomically detects expired leases, records an interrupted/abandoned attempt, issues a new claim token and schedules unfinished jobs. Late responses are rejected by the token check. Stored source/configuration snapshots allow resumption without reopening mutable input files. A crash after remote acceptance may incur a duplicate model call; guarantee coherent local publication, not exactly-once external billing.

Failures become current `error / IT Service Desk / retry-extraction` outcomes with null extraction, an actionable sanitized error and a copyable command including `--db`, `--document-id` and `--attempt-id`. History retains any earlier success with its earlier source/configuration. No automatic model retries initially: this makes every failed attempt and operator action explicit. `retry` creates a new attempt even for an unchanged failed input (`--force` is required to retry a successful current attempt deliberately); `resume` handles unfinished jobs and does not silently retry finished errors. Retrying a historical attempt is refused unless its source/configuration is still desired, with guidance to refresh/reimport intentionally; this prevents stale retries from changing the current revision.

On 429, persist the failure and provider Retry-After cooldown (or a documented bounded fallback); workers delay new calls for that provider across processes, while committed queue work remains readable. Timeouts, 5xx, refusal, malformed output and incomplete responses finish with visible errors; retries are manual after cooldown. HTTP retries are disabled in the transport so there are no unrecorded calls. Unchanged successful reruns reuse the existing current outcome; errors remain visible until explicit retry/refresh. After a failed attempt, do not restore an older successful cache entry as current merely because its inputs match.

### Refresh and routing choices

Fingerprint original bytes separately from effective provider/model/request configuration, prompt bytes, schema bytes, semantic-validator/routing implementation version and policy bytes. Keep secrets outside all fingerprints. A changed source or extraction-affecting setting schedules a new extraction; for simplicity a policy/routing change also re-extracts and reroutes rather than reusing potentially stale policy-derived issues. `refresh --config ... --policy ...` registers only affected desired generations using retained source bytes, with `--force` for an explicit new attempt. Every result records immutable producing configuration and policy; changing concurrency or timeout alone need not refresh already successful facts.

Routing is a deterministic function of validated facts plus source-derived issue flags. Use the five policy rules literally in order. Preserve explicit corrections; unresolved conflicts and missing dates are facts requiring clarification, not extraction transport errors. For an instruction override, use trusted prompt constraints plus conservative source checks for the supplied override patterns and model issues; preserve exact evidence. This is bounded detection of tested patterns, not a claim to detect every possible attack. A manager never implies approval; Security Review's next action explains risk review then a human system-owner decision.

For an otherwise valid withdrawal with ID/date, preserve rule 2 precedence even when other fields are null; do not add an undocumented exception to route it under rule 3. If the ID/date themselves conflict, they are null, so rule 2 does not apply. Unknown absolute-date interpretations remain null with an issue; malformed response date syntax is a validation error. The supplied materials do not resolve the treatment of syntactically valid but impossible calendar dates; keep that edge case flagged for policy clarification rather than inventing a new routing rule or silently correcting it. It is not needed to interpret any supplied example. User decision for this planning revision: leave impossible calendar dates such as 2026-02-30 open for policy clarification; no automatic correction, expected route or invented validation rule is authorized for that unresolved case.

### Outputs, accuracy and remaining decisions

`queue.json` is a JSON array of current envelopes joined by document_id with extraction records; include source_sha256 and attempt_id in both for version checks. Mock response_source is exactly `mock`; real response_source is `openai/<returned-model-id>`. Historical outcomes are accessed through history and an optional separate history export, never mixed into extractions.jsonl. Extra provenance fields may be added to envelopes, not to the fixed extraction schema.

Export both current files from one database read snapshot into a uniquely named staging generation, with a manifest recording hashes and snapshot identity. Publish a ready generation only after both files are complete; use a generation directory plus atomically updated pointer for operational consumers. For final flat `deliverables/` paths, require a quiescent desired queue and a single export lock, copy the matching generation and verify its manifest. Two independent file renames cannot give atomic pair publication to arbitrary readers; the CLI/database is the live review interface. A crash leaves a staged generation or detectable manifest mismatch that `export` can repair, never a claimed consistent pair.

Accuracy uses the 12 scalar schema fields for every one of 21 sources: denominator 252, with a failed extraction contributing zero matches across its 12 expected slots, including expected nulls. Exact match means JSON string equality or both null, without case/whitespace normalization; business_purpose uses the source spans in the oracle table below. Report per-field and whole-record scalar exact matches separately; supporting_quotes and issues receive separate substring/evidence and required-issue checks rather than a fabricated canonical-prose score. Wrong non-null facts, invented facts, missed corrections/conflicts and wrong routes are reported individually. Exact wording mismatch in a faithful purpose paraphrase is counted as an exact-match miss but distinguished from a factual error. Also report routing accuracy separately. No pass percentage is invented, and mock agreement is labeled as plumbing verification. The evaluator never loads mock response files as its oracle.
